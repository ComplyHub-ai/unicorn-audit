# Audit: 2026-07-29 — Executive/Strategic RPC wrapping and remaining DB fixes (direct migration)

**Trigger:** direct continuation of the same-day full-app Playwright audit; closes out the 3 open items parked in [`2026-07-29-fk-relationships-and-tga-status-fix.md`](2026-07-29-fk-relationships-and-tga-status-fix.md) (RLS 403s on 6 executive/strategic views, `get_user_audit`/`list_code_tables` errors, `handle_staff_first_login` 400).
**Scope:** Fixed all 3 previously-parked findings, plus 2 further issues discovered mid-fix (a 7th affected view, and 2 never-populated materialized views). No schema/RLS/trigger change left uninvestigated from the original audit's punch list except the Parent/Child terminology item, which remains an explicit product decision, not a bug.

## Findings

- **`get_user_audit` 404 (`/admin/user-audit`).** The prior audit's "stale schema cache" theory was wrong — confirmed by running `NOTIFY pgrst, 'reload schema'` first (no change) and then inspecting the real PostgREST response body via `browser_network_request` (not just the console, which truncates the actual error): `42P01 relation "public.v_user_audit" does not exist`. Root cause: migration `20260106042554` dropped `public.v_user_audit` as a security fix (to stop exposing `auth.users` via a queryable view) but never updated `get_user_audit` to stop reading from it. Every call has failed since 2026-01-06 — a genuine, long-standing production bug, not something introduced this session.
- **`list_code_tables` 400 (`/admin/code-tables`).** Root cause unrelated to the schema-cache theory too: the function checked the legacy `public.users.role` column instead of `unicorn_role`. `role` is stale, unmaintained data — checked directly against prod: several current Super Admins (including Carl) have a `role` value that doesn't match their actual `unicorn_role` ('Client Child'/'Team Member' vs the correct 'Super Admin'), so the function's own access check was locking out real Super Admins.
- **`handle_staff_first_login` 400 (`/triage-dashboard`).** Two stacked bugs found by tracing a real leftover `staff_provisioning_runs` row (Carl's own, id 9, an April test provisioning run never flagged as first-login-detected):
  1. `user_notifications.dedupe_key` had no unique constraint at all (only a PK on `id`), so the function's `ON CONFLICT (dedupe_key) DO NOTHING` raised `42P10` before ever reaching the notification insert logic.
  2. Once that cleared, a second bug surfaced: the function inserts `channel = 'in_app'` into `notification_queue`, but the table's check constraint only allows `'inapp'|'email'|'both'` — a plain naming typo (confirmed isolated to this one function via a schema-wide grep of function bodies referencing `notification_queue`).
- **403s on `v_executive_*`/`v_strategic_*` views — the prior audit's "not a missing GRANT" conclusion was correct, but for a different reason than suspected.** The real cause: the 4 `v_executive_*` views transitively depend on `mv_compliance_score_daily_30d`, and the 2 `v_strategic_*` objects **are themselves materialized views** (not RLS-backed regular views, despite the naming convention). Postgres materialized views cannot have row-level security at all, and `authenticated` had never been granted `SELECT` on any of the 3 underlying matview objects (confirmed via `has_table_privilege`).
  - A plain `GRANT SELECT TO authenticated` on the matviews would have fixed the dashboards but also auto-exposed them as direct PostgREST endpoints to every logged-in user, including client-portal accounts — a real cross-tenant read of live compliance-score, portfolio-risk, and consultant-capacity data, not a deferred-because-empty gap like some prior RLS findings in this codebase. Flagged to Carl as a genuine security trade-off before proceeding (see Decisions).
  - Fix applied instead: wrapped each affected view in a `SECURITY DEFINER` RPC that checks role before returning data (`public.is_team_leader_or_above()` for the executive views, matching the sidebar's `leadershipOnly` gate; `public.is_super_admin()` for the strategic ones, matching the Strategic Command Centre route's `requireSuperAdmin` gate) — same pattern as `get_user_audit`. The underlying matviews remain ungranted to `authenticated`; only the gated RPCs are.
  - A 7th affected object was found incidentally while verifying the fix live: `v_exec_alignment_signals_7d` (the Executive Dashboard's Alignment Signals panel) has the identical dependency on `mv_compliance_score_daily_30d` and wasn't caught by the original audit pass. Same fix applied.
  - Fixing the permission gate on the 2 strategic matviews (`v_strategic_portfolio_risk`, `v_strategic_capacity_pressure`) revealed a second, deeper issue: both had **never been refreshed/populated since creation** (`55000 has not been populated` once the permission error cleared). Consistent with Strategic Command Centre being one of the previously-orphaned routes wired into the sidebar for the first time in this audit's earlier PR #79 — nobody had ever loaded the page before, so the gap went unnoticed. Ran `REFRESH MATERIALIZED VIEW` on both after confirming with Carl (a data-populating operation, not pure DDL) — safe, read-only recompute from existing tables, no user data modified.

## Decisions

- **Matview access model: SECURITY DEFINER RPC vs. direct GRANT.** Presented to Carl as an explicit choice (quick-but-exposes-cross-tenant-data GRANT vs. more-work-but-correct RPC wrapper vs. leave-as-a-known-gap). Carl chose the RPC wrapper. Rationale recorded here since it sets a pattern: **any object that cannot carry RLS (materialized views in particular) should never be granted directly to `authenticated` in this codebase if it contains cross-tenant data — wrap it in a SECURITY DEFINER function with an explicit role check instead**, mirroring `get_user_audit`'s existing pattern. Worth a KB note if this pattern recurs.
